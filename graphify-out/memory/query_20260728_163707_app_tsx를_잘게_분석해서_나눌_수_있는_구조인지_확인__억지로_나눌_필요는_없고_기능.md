# Q: App.tsx를 잘게 분석해서 나눌 수 있는 구조인지 확인, 억지로 나눌 필요는 없고 기능적으로 분해가 되는지

## Answer

결론: App.tsx는 기능적으로 분해 가능하지만, 작은 컴포넌트 다수로 자르는 방식은 부적절하다. 최신 스냅샷은 약 11.5k lines, useState 103, useRef 58, useEffect 19이며, App은 composition root와 여러 durable async pipeline, recovery/reset transaction, 3.6k-line JSX를 동시에 소유한다. 높은 신뢰도로 추출할 경계는 (1) export/render controller + ExportPanel, (2) broadcast context pipeline—이미 src/app/durableBroadcastContextPipeline.ts가 생겨 App에서 호출됨, 다만 App effect가 여전히 lifecycle/persistence coordinator를 포함, (3) broadcast transcript pipeline, (4) semantic lead refinement pipeline, (5) candidate Pass B controller, (6) candidate audio-event controller, (7) RecoveryPanel/SourceWorkspace 같은 presentation sections이다. 반면 openRecoveredAnalysis는 46개 setter, resetDownstream는 39개 setter, runSignalAnalysis는 19개 setter를 직접 호출하므로 지금 함수만 hook/file로 옮기면 거대한 인자 묶음과 숨은 결합만 생긴다. 이들은 먼저 feature-scoped reducers/state owners와 atomic hydrate/reset actions를 정의한 뒤 분리해야 한다. App에는 source/session identity, phase visibility, cross-feature gates, discard/replace decision, controller composition만 남기는 것이 적절하다. 권장 순서는 export UI/controller → recovery presentation → 현재 context pipeline 추출 완료 → transcript/refinement → candidate detail controllers → session reducers/hydration → runSignalAnalysis 순이다. ReviewStage는 이미 올바른 presentational boundary이므로 억지로 더 쪼갤 필요가 없다. 최신 npm run typecheck는 통과했고 소스 변경은 하지 않았다.
